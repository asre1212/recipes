# Optional Google Drive pilot

The existing app stays at https://asre1212.github.io/recipes/. Nothing is uploaded until the owner explicitly connects and enables the feature. The shared GitHub Pages origin cannot safely hold reusable device authorization for one app path, so setup there is disabled. Existing manual Files export and external-folder backup remain available. No internal backup snapshots or persistent upload outbox are introduced.

## Free hosting and remaining owner setup

Cloudflare Workers Free with SQLite Durable Objects and static assets is the selected path. It supplies a unique workers.dev origin for the complete Recipe app and service, without a domain purchase or credit card. Free-plan limits apply; this is a single-owner pilot. Hugging Face was assessed first alongside Cloudflare; its current Spaces creation/availability and sleep behavior are less suitable for this token service. Existing GitHub Pages is retained.

1. Sign in to Cloudflare (`npx wrangler login`) in the deployment environment. No account was authenticated during implementation. Deploy the code once to establish the unique address; unconfigured API routes fail closed.
2. In the owner's Google Cloud project create a **Web application** OAuth client, configure consent in **Production**, request only `openid email https://www.googleapis.com/auth/drive.file`, and register `https://<unique-worker>.workers.dev/auth/callback`. Complete any Google branding/verification requirements applicable to that project. Testing-mode seven-day access is not suitable.
3. Set `FRONTEND_ORIGIN` to that exact isolated HTTPS origin, `GOOGLE_CLIENT_ID`, `GOOGLE_CONSENT_MODE=production`, and the owner's `ALLOWED_GOOGLE_EMAIL` in `backend/wrangler.jsonc`. Set secrets through `wrangler secret put --config backend/wrangler.jsonc`: `GOOGLE_CLIENT_SECRET` and `TOKEN_ENCRYPTION_KEY` (32 cryptographically random bytes encoded base64url). Keep the root key private; losing it requires reconnecting Google. Never commit secrets or use a frontend token.
4. `npm ci && npm test && npm run build`; then `npx wrangler deploy --config backend/wrangler.jsonc`. The asset binding serves the isolated frontend and the `/api/*` and `/auth/*` routes use the SQLite coordinator. Confirm `/health` and repeat the synthetic and owner-approved live setup checks before enabling real backups.
5. At the old app use Backups → Download encrypted handoff. Keep the current app installed and its data intact. At the isolated address restore that file, choose Replace and restore the section layout. To mirror deliberate omissions, explicitly approve using the handoff as the complete target notebook (this removes target-only recipes), review/confirm, then check the verified handoff receipt. It includes recipes, trial entries, section/category assignments, A–Z/manual preference and manual order. Only after verification choose whether to add the isolated address to the Home Screen. Never clear the old app or uninstall it as a migration step.
6. In the isolated app enter its service origin, connect the allowed Google account once, create/save the recovery file privately, select it to verify, then explicitly enable. Google consent is performed by the owner; no real account connection or recipe upload was performed during implementation.

## Behavior and constraints

- An owner-allowlisted authorization-code flow uses state, PKCE and OIDC nonce. Google offline refresh credentials are authenticated-encrypted in server storage; access tokens remain server-memory only. A nonextractable P-256 device signing key is stored only on the isolated origin. One-time signed requests bind origin/audience, method, path, body digest and expiry. CORS alone is not authentication. Normal token renewal needs no new sign-in; revoked or expired consent can require reconnecting.
- On-device standard compact JWE uses `jose`, RSA-OAEP-256 (3072-bit recovery key) and A256GCM. Every snapshot gets a fresh content key and IV. Only the public recipient key and success metadata persist in the app. The recovery private key is a user-held file, never browser-persisted or sent upstream. Its loss makes these encrypted copies unrecoverable.
- A short debounce backs up from the existing live recipe store while open and online. Offline edits are picked up on the next online/open opportunity. There is no closed-app iPhone execution promise, backup payload cache, persistent outbox or automatic internal recovery snapshot.
- Drive scope is limited to Recipe-created files. A visible, private `Recipe encrypted backups` folder holds opaque `.jwe` files. Newly uploaded bytes, size and SHA-256 are verified by download before either known-good copy is pruned. Only app-owned manifest entries may be removed. Failed upload, checksum, permission, cleanup or network checks retain prior good copies; failures can temporarily leave more than two copies. Unrelated files are never deleted. Credentials are not forwarded across download redirects.
- Restores decrypt/authenticate and validate before preview. Wrong keys/tampering do not write data. Replacement and layout restoration require explicit approval. Manual encrypted/plain Files exports still work independently.
- `AUTH_EPOCH` can revoke all previously authorized devices. Disable stops future uploads; Disconnect removes that device authorization, preserving encrypted files. Server logs must not contain request bodies, OAuth grants, tokens or keys; observability is disabled in the supplied configuration.

## Reuse

`public/remote-backup-core.js` exports `remoteScheduler({readConfig, readSnapshot, seal, upload, digest, writeStatus, online, visible})`. It serializes work, debounces saves, fingerprints snapshots and retries transient failures without persisting payloads. `public/remote-crypto.js` is the versioned JWE adapter. `backend/drive.js` implements private-folder validation, verified two-copy rotation and server-side renewal; it is single-owner and must not be reused as a multi-tenant service without a separate authorization design. Other repositories were not changed.

## Verification status

Automated tests use synthetic Google/Drive responses and disposable recipe records; they do not establish a live Google authorization or upload. Worker build/dry-run passes. Cloudflare CLI reported not authenticated. Production Google project/consent, the isolated Worker deployment, actual Drive upload/download/restore and physical iPhone Home Screen behavior remain owner-setup dependent. Do not describe this pilot as live automatic backup until those steps are verified.

To repeat the browser test, generate a **disposable localhost-only** TLS key/certificate outside the repository, set `RECIPE_TEST_CERT_DIR` to its directory, build, run `node tests/remote/server.mjs`, and run `python tests/remote/browser.py` with Playwright WebKit installed. The fixture blocks real Google navigation and overrides bundled recipes with two synthetic records. It tests UI opt-in, fresh recovery-file download/verification, exactly two copies after edits, offline catch-up, server-side refresh without another consent, wrong-key/tamper rejection, explicit restore approval, and encrypted handoff receipt verification. Test credentials and downloaded synthetic files must never be deployed.
